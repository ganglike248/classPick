[ 프로젝트 시작 방법 ]
────────────────────────────────────────────────────────────────────────────────

  1. 의존성 설치 (최초 1회 또는 package.json 변경 시)
     cd e:/programing/Pro/project/classPick
     npm install

  2. 개발 서버 실행 (로컬 테스트)
     npm run dev
     → 브라우저에서 http://localhost:5173 접속

  3. 배포용 빌드
     npm run build
     → dist/ 폴더에 정적 파일 생성됨

  4. 빌드 결과물 미리보기
     npm run preview
     → 빌드된 결과를 로컬에서 확인

[ 모드 설명 ]
────────────────────────────────────────────────────────────────────────────────

  ■ 자유 연습 모드
    - 과목을 직접 설정하고 수강신청 화면을 자유롭게 체험
    - 시간 제한 없음, 반복 연습 가능

  ■ 체험 모드 (지금 바로 체험하기)
    - 과목 설정 없이 임의 6개 과목으로 바로 체험 가능
    - 마감 타이머 없음 (난이도 없음), 전 과목 신청 시 자동 완료
    - 결과는 일회용 (랭킹 저장 안 됨), 체험 후 기존 설정 자동 복원

  ■ 실전 모드
    - 10시 대기 화면 → 흰 화면(1~7초) → 캡차 인증 → 과목 신청 순서로 실제 환경 재현
    - 랜덤 마감 타이머, 학점 초과 제한 등 실제와 동일한 조건
    - 결과 화면에서 소요 시간 확인 가능

  ■ 랭킹 도전 모드
    - 실전 모드와 동일한 환경에서 기록 측정
    - 전 과목 신청 성공 시에만 Firebase에 기록 저장
    - 순위표에서 다른 사용자와 소요 시간 비교 가능
    - challengeData.js의 CHALLENGE_ID(현재 "v2")로 랭킹판을 구분함.
      과목 구성이나 캡차 지연처럼 소요 시간에 영향을 주는 변경이 생기면
      CHALLENGE_ID를 올리고 CHALLENGE_VERSIONS에 이전 버전 안내 문구를 남김
      → 서로 다른 조건의 기록끼리 섞여 비교되는 걸 방지 (2026-07, semesterId
      방식에서 전환. 상세 배경은 하단 커밋 기록 참고)

  ■ 명예의 전당 / 손풀기 반응속도 게임 (2026-07 추가)
    - 명예의 전당: 홈 화면·랭킹 도전 화면에서 현재 챌린지 버전 상위 3위와
      누적 참여자 수를 보여줌 (HallOfFame.jsx)
    - 반응속도 게임: 홈 화면 사이드바 4번째 카드. 기록 저장 없는 순수 놀이용
      (ReactionGame.jsx)

  ■ 피드백 (2026-07 추가)
    - 하단 푸터에서 로그인 없이 익명으로 피드백 메시지 전송 가능
    - /feedback 페이지에서 관리자(FEEDBACK_ADMIN_EMAIL 계정)만 로그인 후
      조회/삭제 가능. 강제력은 firestore.rules의 feedback 컬렉션 규칙이 담당


[ 데이터 저장 방식 ]
────────────────────────────────────────────────────────────────────────────────

  ■ localStorage (브라우저 로컬)
    - 메인 상태 키: "courseRegistrationPracticeState"
    - 결과 임시 키: "classPick_practiceResult" (랭킹 도전 모드 결과 일회성 저장)
    - 체험 백업 키: "classPick_trialBackup" (체험 모드 진입 전 기존 설정 백업)
    - 프리셋 키: "preset1", "preset2", "preset3" (최대 3개)
    - 브라우저 개발자 도구 > Application > Local Storage 에서 확인 가능

  ■ Firebase Firestore (서버)
    - rankings 컬렉션: 랭킹 도전 모드 기록 (익명)
      · 저장 데이터: uid, 닉네임, challengeId, startedAt/endedAt(서버 타임스탬프),
        status(in_progress/completed), 신청 결과(result)
      · uid 기준 최고 기록 1개만 순위표에 노출 (rankingUtils.fetchRankings에서
        정렬 후 필터링, 문서 자체는 삭제하지 않는 한 남아있음)
      · rankingUtils.js에 challengeId별 1분 TTL 클라이언트 캐시 있음 (도전 완료·
        닉네임 변경·기록 삭제 시 즉시 무효화, 랭킹 페이지 새로고침 버튼은
        forceRefresh로 캐시 우회)
      · Firebase 익명 인증(Anonymous Auth) 사용
    - feedback 컬렉션: 사용자 피드백 메시지 (익명 작성 가능)
      · 저장 데이터: message(최대 1000자), createdAt
      · 조회/삭제는 FEEDBACK_ADMIN_EMAIL 계정(이메일 로그인)만 가능
        (constants/site.js ↔ firestore.rules 두 곳에 이메일이 일치해야 함)


[ 배포 전 확인사항 (닉네임/랭킹 개선, 2026-07) ]
────────────────────────────────────────────────────────────────────────────────

  ■ firestore.rules 재배포 필수
    - 본인 완료 기록의 닉네임 수정/삭제를 허용하도록 규칙이 바뀜
    - Firebase Console > Firestore Database > Rules 탭에 firestore.rules 내용을
      다시 붙여넣고 게시해야 실제로 적용됨 (코드만 바뀐 것으론 반영 안 됨)

  ■ Firestore TTL 정책 설정 (신규)
    - 도전 시작 후 완료하지 않고 이탈한 "in_progress" 세션이 방치되는 문제 해결용
    - rankingUtils.js의 startChallengeSession()이 문서 생성 시 expiresAt
      필드(생성 시각 + 2시간)를 함께 저장하도록 변경됨
    - Firebase Console > Firestore Database > TTL 탭 (또는 gcloud firestore
      fields ttls update 명령)에서 rankings 컬렉션의 expiresAt 필드를 TTL 대상으로
      지정해야 자동 삭제가 실제로 동작함 (필드만 있고 TTL 정책을 안 켜면 정리되지 않음)
    - finishChallengeSession()에서 완료 처리 시 expiresAt 필드를 함께 제거하므로
      완주한 랭킹 기록이 TTL로 잘못 삭제될 일은 없음


[ 광고 연동 (2026-07-28 도입) ]
────────────────────────────────────────────────────────────────────────────────

  ■ 지금 코드에 이미 들어가 있는 것 (계정/승인만 하면 바로 켜짐)
    - 카카오 애드핏(AdFit) 하단 고정 배너: App.jsx에서 사이트 전체에 노출.
      단, /register(실제 수강신청 시뮬레이션 화면)는 시간 압박이 있는 화면이라
      제외함 (실전 몰입도를 해치지 않기 위함)
      ※ 애드핏의 PC 웹 매체는 상품 선택에서 "배너"만 제공되고 별도의
        "앵커 배너" 상품이 없어(모바일 전용으로 보임), 일반 배너 광고 단위를
        App.jsx에서 position:fixed로 화면 하단에 직접 고정시켜 앵커처럼 보이게
        구현함 — 즉 ANCHOR용 광고 단위도 애드핏 대시보드에서는 그냥 "배너"로
        만들면 됨
    - 카카오 애드핏 본문 배너: ResultPage(결과 확인 직후), RankingPage(순위표
      확인 중) 각각 한 자리씩. 둘 다 자연스럽게 잠깐 멈추는 지점이라 선택함
    - 구글 애드센스 로더 스크립트: vite.config.js가 빌드 시점에 VITE_ADSENSE_CLIENT_ID가
      있으면 index.html의 <head>에 정적으로 직접 삽입 (없으면 아무 동작 안 함).
      ※ 처음엔 main.jsx에서 React 마운트 후 JS로 태그를 넣었는데, 애드센스의
      "사이트 소유권 확인"이 정적 HTML만 보고 JS로 나중에 넣은 태그는 못 찾아서
      "사이트를 확인할 수 없습니다" 오류가 났음 → 빌드 시점에 index.html 자체에
      심는 방식으로 교체함
    - src/components/common/AdFitBanner.jsx: unitId가 비어 있으면 아무것도
      렌더링하지 않아, 광고 단위를 발급받기 전에도 레이아웃이 깨지지 않음
    - public/ads.txt: 애드센스 승인 후 채워 넣을 자리만 마련해둠 (심사 전엔 불필요)
    - PrivacyPage.jsx에 광고 서비스(쿠키 수집 등) 관련 고지 추가함
      (광고 붙일 때 개인정보처리방침 갱신은 필수 — 안 하면 애드센스 정책 위반)

  ■ 실제로 광고를 띄우려면 (계정 만들기부터)

    1) 카카오 애드핏 (adfit.kakao.com) — 승인이 거의 즉시라 먼저 진행 추천

       b. 심사 통과 후 "광고 단위 만들기"에서 배너(728x90 권장) 2개 생성:
          - 하나는 하단 고정용(코드에서 이미 position:fixed로 고정 처리함)
          - 하나는 결과/랭킹 페이지 본문 삽입용
       c. 각 광고 단위의 "DAN-..." ID를 복사
       d. .env (로컬)와 Netlify 배포 환경변수(Site settings > Environment
          variables) 양쪽에 VITE_ADFIT_UNIT_ID_ANCHOR / VITE_ADFIT_UNIT_ID_CONTENT로
          붙여넣고 재배포 → 코드 수정 없이 바로 광고 노출 시작

    2) 구글 애드센스 (adsense.google.com) — 승인에 며칠~몇 주 걸릴 수 있어 병행 추천
       a. 계정 생성 후 사이트 추가, 발급된 "ca-pub-XXXXXXXXXXXXXXXX" 확인
       b. .env와 Netlify 환경변수에 VITE_ADSENSE_CLIENT_ID로 채우고 재배포
          → 이 시점부터 심사용 로더 스크립트가 index.html 정적 HTML에 실제로
          박혀서 배포됨 (승인 전엔 광고 노출 안 됨). 애드센스 화면에서
          "코드를 삽입했습니다" 체크 후 "검토 요청" 클릭까지 해야 심사가 시작됨
       c. 승인 이메일을 받으면 애드센스 대시보드 "ads.txt 시작하기"에서 정확한
          문구를 복사해 public/ads.txt에 붙여넣고 배포
       d. 애드센스 대시보드에서 "자동 광고" 켜거나 원하는 위치에 수동 광고
          단위를 추가 (수동 배치가 필요하면 다시 요청하기)

    ※ 로컬 .env는 git에 커밋되지 않으므로, Netlify(실제 배포)에도 같은 값을
      별도로 등록해야 실제 사이트에 광고가 뜸 — 둘 중 하나만 하면 반쪽짜리로
      동작 안 함


[ 버전 관리 규칙 ] (2026-07-28 도입)
────────────────────────────────────────────────────────────────────────────────

  ■ 버전 형식: MAJOR.MINOR.PATCH (예: 1.6.28)
    - package.json의 "version" 필드가 유일한 기준(source of truth)
    - vite.config.js가 빌드 시 package.json의 version을 읽어 __APP_VERSION__
      전역 상수로 번들에 주입함 → 최상단 헤더(TopBand.jsx, "수강신청 연습
      시스템" 제목 옆의 작은 회색 글씨)에 표시되는 버전은 package.json만
      바꾸면 자동으로 같이 바뀜 (코드에 버전을 중복으로 하드코딩하는 곳 없음)

  ■ MAJOR (첫 번째 숫자)
    - 1로 고정. 서비스 성격이 완전히 바뀌는 수준의 개편이 있을 때만 논의 후 올림
    - 랭킹 도전 모드의 CHALLENGE_ID("v2" 등, challengeData.js)와는 별개의
      숫자이니 혼동하지 않기 (그쪽은 랭킹 공정성 구분용 버전, 이건 앱 배포 버전)

  ■ MINOR / PATCH 증가 규칙 — 새로운 변경사항을 반영할 때마다 적용
    - 사용자에게 의미 있는 변경(기능 추가/수정, 버그 픽스, 디자인 조정 등)을
      하나 반영할 때마다 PATCH를 1 올린다 (예: 1.6.28 → 1.6.29)
    - 그중에서도 "큰 변경"이면 PATCH 대신 MINOR를 1 올린다 (예: 1.6.28 → 1.7.0
      이 아니라 1.7.28처럼 PATCH는 그대로 두고 MINOR만 올림 — 0.1을 더하는 것과
      동일한 계산)
      "큰 변경"의 기준:
        1) 완전히 새로운 모드/기능(신규 페이지 + 사용자가 겪는 새 흐름)이
           추가되는 경우 (예: 실전 모드, 체험 모드, 피드백 시스템)
        2) 화면 전체/전면 리디자인 수준의 디자인 개편인 경우
      그 외 대부분의 커밋(문구 수정, 버그 픽스, 기존 화면 다듬기, 성능 개선,
      리팩터링 등)은 PATCH만 올리는 일반 변경으로 취급한다
    - 버전을 올릴 때는 package.json의 "version" 필드만 수정하면 됨
      (build 스크립트/UI 뱃지는 자동 반영)

  ■ 사용자용 업데이트 내역(src/data/updateLog.js)도 함께 챙기기
    - 최상단 헤더의 "v{버전} · 업데이트 내역" 버튼(TopBand.jsx, 모든 페이지에
      공통 노출)이 이 파일의 UPDATE_LOG 배열을 그대로 보여줌
    - 새 항목을 추가할 때 원칙:
      · 개발 내부 작업 단위가 아니라, 사용자가 실제로 체감하는 변화만 적기
      · 관련된 변경은 날짜/주제 단위로 하나의 entry(title+date)로 묶되,
        서로 다른 버전에서 추가된 기능이면 items 배열 안에서 각 항목마다
        해당 기능이 추가된 version을 명시하기 ({ version, text } 형태)
      · 최신 항목을 배열 맨 앞에 추가하기 (배열 순서 = 화면 표시 순서)
    - "큰 변경"이 아니어도 사용자가 느낄 수 있는 변화라면 업데이트 내역에는
      적는 게 좋음 (버전 규칙과 업데이트 내역 작성 여부는 별개 판단)
